# 应用更新

## 结论

能实现，而且几乎不用自己写。Mygo v0.6.0 已经内置了完整的签名自更新：

- `mygo keygen` 生成 Ed25519 密钥对
- `mygo build` 打出带签名的更新包、增量包（delta）和 `update-<target>.json` 清单
- `mygo.Updater.Check / Install` 负责下载、校验签名、原地替换、重启
- `plugins/updater/native` 提供一个原生更新窗口，不需要 WebView

需要做的只是：配置 `updates`、准备一把签名密钥、加一条发布流水线，再在设置页
接上检查和安装。

## 现状

- `mygo.json` 没有 `updates` 配置，`mygo build` 目前不会生成更新包。
- 没有 GitHub Actions，`build/` 里的产物是本机打出来的。
- 版本号有两处：`mygo.json` 的 `0.1.0` 和 `internal/about/about.go` 的
  `Version = "0.1"`，两者已经不一致。
- 没有 `CHANGELOG.md`，而 Mygo 的更新说明正是从它的 `## <version>` 段落里取的。
- 项目使用原生 UI（`github.com/egoist/mygo/ui`），没有用 `mygo.Use`。

## 发布模型

使用 GitHub Releases 作为更新源，标签为 `v<version>`，例如 `v0.2.0`。
`mygo.Updater` 默认读取仓库 **latest release** 里的
`update-<target>.json`，不需要额外的服务端。

清单按平台区分，每个平台只读自己那一份：

| 平台 | 清单 target |
| --- | --- |
| Linux amd64 / arm64 | `linux-amd64` / `linux-arm64` |
| Windows amd64 / arm64 | `windows-amd64` / `windows-arm64` |
| macOS | `darwin-universal` |

`mygo build` 同时会生成：

- `<name>-<version>-<target>.tar.gz`：签名过的完整更新包
- `<from>-to-<version>-<target>.delta`：从最近 3 个已发布版本升级的增量包
- `update-<target>.json`：版本、日期、说明、包地址、大小和签名

应用下载时优先用 delta；delta 失败或不是从该版本升级时自动回退整包。

## 版本号

- `mygo.json` 的 `version` 是唯一版本来源，应用里通过
  `mygo.App.Version()` 读取。
- 正式发布时 CI 用标签里的版本注入，例如 `v0.2.0` → `0.2.0`，避免手改
  文件后忘了提交。
- 发布后 main 上的 `version` bump 到下一个开发版本（如 `0.3.0`）。

## 发布流水线

### 一次性准备

```bash
go tool mygo keygen          # 生成 mygo-update.key / mygo-update.pub
```

- `mygo-update.pub` 的内容提交进 `mygo.json` 的 `updates.publicKey`。
- `mygo-update.key` 只放进 GitHub Secret `MYGO_UPDATER_PRIVATE_KEY`
  和密码管理器，绝不提交。密钥丢失后所有已安装用户都无法再更新。
- 密钥泄露等同于任何人都能向用户推送任意代码，必须立刻轮换并发布一个
  带新公钥的版本（旧版本无法自动接受新密钥，需要用户手动重装一次）。

`mygo.json` 增加：

```json
{
  "name": "MyLock",
  "identifier": "dev.babyly233.mylock",
  "version": "0.2.0",
  "out": "build",
  "updates": {
    "publicKey": "<mygo-update.pub 的内容>",
    "github": "BabyLy233/mylock",
    "changelog": "CHANGELOG.md"
  }
}
```

### `.github/workflows/release.yml`

触发：推送 `v*` 标签，或手动指定版本。

1. `prepare` 作业：`gh release create v0.2.0 --draft`。
   先建草稿，避免矩阵里各平台并发执行 `-upload` 时各建各的草稿。
2. `build` 作业，矩阵：
   - `ubuntu-latest` → `linux/amd64`、`linux/arm64`
   - `windows-latest` → `windows/amd64`、`windows/arm64`
   - `macos-latest` → `darwin/universal`

   Windows 和 macOS 必须在各自系统上构建：NSIS 安装包和 `.dmg` / 签名
   在 Linux 上会被跳过。
3. 每行先把标签版本注入 `mygo.json`，再执行：

   ```bash
   jq --arg v "$VERSION" '.version = $v' mygo.json > mygo.json.tmp
   mv mygo.json.tmp mygo.json
   go tool mygo build -platform "$PLATFORM" -upload
   ```

   环境变量：`MYGO_UPDATER_PRIVATE_KEY`、`GH_TOKEN`（GitHub 默认提供）。
   `-upload` 会先上传更新包 / delta，最后上传清单。
4. `publish` 作业：等所有平台传完，
   `gh release edit v0.2.0 --draft=false --latest=true`。
   应用下一次检查就能看到。

macOS 要真正可分发自更新，还需要 `macos.signingIdentity` 和
`macos.notarize`（Apple Developer ID + `notarytool` 凭据），否则用户会
遇到 Gatekeeper 提示，且签名 / 公证信息无法随 delta 保持。这是外部准备项，
不是代码问题。

### `CHANGELOG.md`

手工维护 `## 0.2.0` 段落，作为更新说明。建议同时写一个 `## Unreleased`
段落，发版时改名并补日期。段落标题必须与版本号精确对应，否则
`mygo build` 会报错。

## 客户端改动

### 1. 版本号统一

- `internal/about` 的 `Version` 改为运行时读取 `mygo.App.Version()`，
  `UserAgent` 使用同一个值。现在 `0.1` 和 `0.1.0` 不一致。
- 设置页显示当前版本，具体见 [`版本显示.md`](版本显示.md)。

### 2. 设置页的“更新”一节

建议直接用 `native.Plugin`，它负责：

- 启动 10 秒后检查一次，之后每天一次
- 显示版本号、日期和 Markdown 更新说明
- “安装更新 / 稍后提醒 / 跳过此版本”
- 下载进度和重启
- 自动下载、自动安装的偏好

接入方式：

```go
import (
    "github.com/egoist/mygo"
    "github.com/egoist/mygo/plugins/updater/native"
)

mygo.Use(native.Plugin)
```

设置页再放一个“检查更新”按钮，调用 `updater.CheckForUpdates()` 即可。
如果不想用插件，也可以直接用 `mygo.Updater.Check / Install` 自绘进度，
但没必要先走这条路。

### 3. 不可自更新时的说明

`mygo.Updater.Enabled()` 为 false 时（`.deb` 安装在 `/opt`、AppImage、
无写权限的 `/Applications`），设置页要显示原因，而不是让按钮静默失败：

- Linux：只有 `install.sh` 或解压到用户可写目录的安装能自更新；
  `.deb` 由包管理器更新。
- Windows：NSIS 的 per-user 安装（`%LOCALAPPDATA%\Programs`）可以；
  放在 `Program Files` 的便携版不行。
- macOS：应用装在无写权限的 `/Applications` 时不行，需要用户级安装
  （`~/Applications`）或管理员权限。

## 改动清单

- `mygo.json`：增加 `updates`，版本改为下一个正式版。
- `CHANGELOG.md`：新建。
- `.github/workflows/release.yml`：新建。
- `internal/about/about.go`：版本改为运行时读取。
- `main.go`、新建 `main_update.go`：设置页“更新”一节、检查入口。
- `README.md`：补“应用更新”和密钥说明。

## 实施顺序

1. **发布基础设施**（1–2 天）：密钥、`updates` 配置、CHANGELOG、workflow。
   先手动发一个 `v0.2.0`，确认 `install.sh` 安装的 Linux 包能在应用里
   看到更新。
2. **更新 UI**（1 天）：接 `native.Plugin`，设置页加“检查更新”。
3. **收尾**：版本号统一、README、发布检查清单。

## 风险与限制

- **密钥管理**：私钥丢失 = 所有用户永久失去更新能力；私钥泄露 = 任意代码
  可被推送给用户。必须备份，并限制 GitHub Secret 的访问。
- **macOS**：正式分发需要 Developer ID 签名和公证；装在无写权限的
  `/Applications` 时不能自更新。
- **Linux**：`.deb` 不能自更新，由包管理器负责。
- **Windows**：只有 per-user 安装或可写目录能自更新。
- **依赖 Mygo 的更新格式**：`updater` / 归档格式由 Mygo 决定，升级 Mygo
  时留意变更。
- **GitHub 作为更新源**：latest release 的清单走静态下载地址，不消耗
  GitHub API 速率；但如果以后需要多频道或灰度，才会用到 API。

## 验收

- [ ] `v0.2.0` 发布后，0.1.x 的正式版能检查到并安装，重启后版本正确。
- [ ] 同频道连续版本只下载 delta；delta 失败时自动回退整包。
- [ ] 篡改清单、归档、签名、尺寸任意一项都会拒绝安装且原应用可继续运行。
- [ ] `.deb` 安装和开发构建显示“无法自更新”及原因，不出现误导性按钮。
- [ ] Windows 更新时正在运行的可执行文件被正确替换，旧文件下次启动清理。
- [ ] macOS universal 更新后 `.app` 完整，签名 / 公证未被破坏（启用签名后）。
