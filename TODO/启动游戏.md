# 启动游戏

## 现状

「已安装模组」页顶部有两个按钮：**启动原版游戏** 和 **启动模组版游戏**。

两种启动的区别写在 `gameinfo.gi` 里，不是传给 Steam 的参数——游戏只从那里
读它要加载什么：

- 带模组：写当前 profile 的搜索路径（和设置页那个「应用模组路径」同一个动作）。
- 纯净：写回游戏自带的那份（`internal/game` 的 `vanillaSection`），模组目录
  和两行 `Mod` 都不写，连本应用自己的标记也不留。所以纯净启动之后
  `ReadGameInfo` 报 `Markers` 和 `ModPaths` 都是 false，模组页会顶上那条
  「游戏没有在加载模组目录」的提示——这是对的，不是出错。

启动本身走 `steam://run/1422450//`，交给平台的启动器：Windows 是 Steam 目录
下的 `steam.exe`，Linux 是 `steam.sh`，macOS 是 `open`；游戏目录是手动指定、
没有 Steam 根目录时退到 `rundll32.exe url.dll,FileProtocolHandler` /
`xdg-open`。

### 游戏在跑的时候不动模组

`internal/game` 的 `Running` 每两秒看一次进程表（Linux 读 `/proc`，Windows 读
toolhelp 快照，macOS 问 `ps`；游戏是 Windows 程序，所以名字始终是
`deadlock.exe`，Linux / macOS 上由 Proton / Wine 带着跑）。它在主线程之外跑：

- 模组页的开关、两个启动按钮、设置页的「应用模组路径」、商店的「安装」都禁用，
  页面上写明原因。
- 动作真正落地前还会再问一次 `Running`，因为游戏可能在两次轮询之间起来：
  开关在搬文件之前问，「安装」在下载解压之后、写进游戏目录之前问，启动在写
  `gameinfo.gi` 之前问。被拦下时页面显示「游戏正在运行，先退出游戏再…」。

### 纯净启动之后自己改回来

纯净启动成功后在设置里记下 `vanillaPending`（这次不带模组）和 `vanillaSeen`
（它的游戏真的起来过）。轮询看到游戏从有到无、并且 `vanillaSeen` 为真时，把
当前 profile 的搜索路径写回去，提示「游戏已关闭，已恢复加载模组。」。

不看到游戏起来就不写回：Steam 接了请求但游戏还没起（更新、排队）时，提前写回
会让这次纯净启动反而加载模组。进程起来过一次之后，之后「没在跑」就只可能是
这次会话结束了，包括应用中途关掉、下次启动时游戏已经退出的情况——两个标记都
在配置文件里，重新启动会接着等 / 直接写回。

切换模组开关、应用模组路径、从商店安装、再点一次带模组启动，都会取消这个等待：
它们已经把模组路径写回去了，不再有一次「等它结束」的会话。

## 还没做的

- **启动参数。** 原版能带 `-condebug` 之类的附加参数，Flatpak 下还会自动补上
  `-condebug`。这里恒定为空。
- **等游戏真的起来。** 原版会轮询进程，超时没起来就报错；这里只等到启动器把
  请求交出去（最多 8 秒），之后游戏起没起是 Steam 的事。轮询只用来跟会话，
  没等到游戏起来也不会报错。

## 已经确认过的

- 直接 exec 游戏本体还是走 `steam://`：选了后者。Steam 管更新、管运行库，
  游戏也指望是它启动的。
- Linux 上 `steam.sh` 在前台跑（脚本最后是 `"$STEAMROOT/$STEAMEXEPATH" "$@"`，
  没有 `&` 也没有 `exec`），所以 Steam 没在运行时它会一直挂着——这正是
  `handOverWait` 那个上限存在的原因。
- 启动器的输出写到临时文件而不是管道：实测子进程在管道的读端关掉之后，
  下一次往 stderr 写就会被 SIGPIPE 杀掉，而我们的窗口关掉时启动器往往还在跑。
- 进程名用 `deadlock.exe` 而不是 `deadlock`：Linux 上直接查本体进程会漏掉
  Proton 下的游戏，原项目也是这么查的。
