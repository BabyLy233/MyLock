# 多 Profile（配置档）

## 现状（已完成，2026-10-21）

「模组管理」页顶部现在显示当前配置档，旁边的「切换 / 管理…」打开管理
对话框。默认配置档就是 `citadel/addons` 根目录，另外的配置档是它下面的
`profile_*` 文件夹。

已实现的行为：

- **当前配置档**存在 `config.json` 的 `profileFolder` 里（空 = 默认配置档）。
  所有模组操作——启用开关、删除、商店安装、启动前写 gameinfo、纯净启动后
  恢复、页面读取——都使用打开操作时固定下来的那个配置档，不会中途读配置。
- **新建**：在 addons 目录下建空目录
  `profile_<毫秒时间戳>_<随机串>_<名字 slug>`，写进
  `~/.config/mylock/profiles.json`（名称、描述、创建/最后使用时间），**不自动
  切换**过去。名字不能为空、不能重名（忽略大小写）；文件夹撞名会重试。
- **切换**：用目标配置档的 `SearchPaths()` 重写 gameinfo.gi，再读它的模组
  清单，最后记住选择并更新 `lastUsed`。写入 gameinfo 失败时不会改当前配置档；
  游戏运行中拒绝。切换会取消纯净启动的等待（因为它重新写了模组路径）。
  设置文件写失败时当前这次运行仍然用新配置档，错误显示在管理框或模组页。
- **删除**：先确认。默认配置档不能删。删当前配置档时先把 gameinfo 切回默认
  配置档，再删 `addons/<folder>` 和 `addons2..10/<folder>`，最后移除元数据。
  游戏运行中拒绝。文件夹删到一半失败时保留条目，并已经处于默认配置档。
- **同步**：启动查找游戏时、以及每次打开管理框时扫描 addons 下的 `profile_*`
  目录。陌生的目录按目录名恢复成配置档（`profile_<时间戳>_<随机串>_<名字>`
  解析出名字），已有条目的名称/描述保留。文件夹不见了的条目仍然列出来，
  标成「目录不存在」，可以删除条目。
- **安全**：配置档目录必须是 `profile_*`、不含路径分隔符、不是 `.`/`..`；
  删除和切换都会再校验一次，防止手改过的 `profiles.json` 指到 addons 之外。
- 商店安装在下载期间如果用户切换了配置档，模组仍然落在开始时那个配置档，
  但游戏配置和页面列表跟随「现在」的配置档。

测试覆盖在 `internal/app/profiles_test.go` 和 `internal/config/profiles_test.go`。

## 还没做的

- **重命名 / 改描述**：目前只能在新建时写。数据层已经分开（`Name` 与
  `Folder`），改的只是 `profiles.json`，需要再加一个编辑对话框。
- **导入 / 分享配置档**：原项目走 DMM 服务端的 `getProfile` / `shareProfile`，
  依赖服务端 API，先不做。
- **配置档级别的批量操作**：全部启用 / 全部停用、排序。
- **删除时正在商店安装**：现在没有显式拦截；安装目标目录被删会让那次安装
  报错（文件写入失败），不会静默成功。要更友好可以在删除前检查
  `store.installing`。
- 默认配置档与 Tauri 版互相识别：目录格式已经一致，靠同步即可；Tauri 版
  建的配置档能被扫到，我们建的它也能读。

## 原项目怎么做（行为参考）

- 顶部工具栏有当前 profile 选择器，点开是管理对话框（实验性功能
  `profile-management`）。
- 每个 profile 有：名称、描述、创建/最后使用时间、是否默认、`folderName`、
  启用模组表和本地模组列表。
- 默认 profile 的 `folderName` 是 `null`，文件就在 `citadel/addons` 本身，
  不能删除。
- 新建：在 `citadel/addons` 下创建空目录
  `profile_<时间戳>_<随机串>_<名字 slug>`，不自动切换过去。
- 重命名/改描述只改显示信息，目录名不动。
- 删除：默认 profile 拒绝；删的是当前 profile 时先切回默认；然后把所有分片
  根下的该目录（`addons/<folder>`、`addons2..10/<folder>`）一起删掉。
- 切换：保存当前 profile 的启用状态 → 迁移到分片 → 把目标 profile 的搜索
  路径写进 `gameinfo.gi` → 重新读目标 profile 的模组列表。游戏运行中拒绝。
- 另有：从文件系统同步、导入/分享。

## 存储：为什么不是 SQLite

mygo v0.6.0 自带 `plugins/sqlite`（无 cgo、预编译库、FTS5），本机实测可用。
但配置档和模组元数据都不大，现阶段 JSON 更合适：

- `config.json` 和 `profiles.json` 都走 `internal/config` 已有的原子写入
  （临时文件 + rename），`settingsMu` / `profilesMu` 各管一个文件的写入。
- 启用状态的真值在 `.dmm.json`，必须保持文件形式（和 Tauri 版共用）；
  SQLite 只能当索引，多一份数据就多一层一致性要维护。
- 引入原生库的代价：首次构建/测试下载预编译库、打包要带上并签名、平台下限
  Linux glibc ≥ 2.28 / macOS ≥ 12、还要维护 schema 迁移。

真正值得引入的时机是本地 GameBanana catalog（见 `TODO/筛选.md` 末尾）：
约 9 千条模组、facets、FTS5 离线搜索——那才是原项目用 SQLite 的地方。

## 约定

- **默认 profile 的目录就是 addons 根目录**，任何删除逻辑都显式拒绝
  folder 为空。
- 目录名必须是 `profile_*` 且不含 `/`、`\`、`..`。
- 两个 profile 的同名模组互不影响：各有自己的清单和文件；模组元数据
  （名字/角色）以后按模组 id 全局共享，见 `TODO/角色皮肤.md`。
- 切换 profile 不会复制文件；新建的 profile 是空的，只共享商店和元数据。
- 兼容性：`.dmm.json` 和分片布局保持原样，Tauri 版应能直接读我们建的
  profile 目录。
