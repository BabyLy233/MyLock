# 商店筛选

## 现状（已完成，2026-10-21）

商店（`main_store.go`）现在有三层筛选，都在商店页类型标签下面的一行里：

- **分类**：下拉，选项是当前类型（模组 / 音效 / 制作中）的根分类，从
  `Mod/Categories` 实时读取；`全部分类` 表示不筛选。
- **子分类**：选了根分类后才出现，从 `Mod/Categories?_idCategoryRow=<根 id>`
  读取，按根分类缓存（`subsCache`）。Skins 下面是 44 个英雄，HUD、Model
  Replacement 下面是部件。
- **隐藏 NSFW**：复选框，**默认不勾**（与原项目一致）。勾上后只影响当前页，
  不做新请求，旁边显示「本页隐藏了 N 个」。

实现上的要点：

- **浏览**走服务端过滤：请求带 `_aFilters[Generic_Category]=<id>`。选子分类
  时只发子分类 id，API 自己就把它当成更具体的筛选。
- **搜索**走 API 的搜索接口，它接受 `Generic_Category` 之后**静默忽略**，所以
  搜索结果的分类和子分类在客户端按 `Category` / `Subcategory` 名字过滤
  （`matchesFilter`）。子分类名只在对应根分类下有意义，所以两者要一起匹配。
- **NSFW** 没有服务端过滤，只能客户端做。判据是
  `_sInitialVisibility ∈ {warn, hide}`，已解析成 `gb.Submission.NSFW`。
  原始页保存在 `raw`，切换复选框只重新过滤，不再请求。
- 切换类型（模组 / 音效 / 制作中）会清空已选分类和子分类并重新读树，因为三类
  的分类树各自独立。
- 分类树读不到时列表照常可用，筛选行里显示「读不到分类：…」和「重试」。

**分页注意**：服务端筛选时 `Total` / `More` 是服务端按筛选后的结果给的，页是
对的。搜索的客户端过滤会让当前页少于 15 条，而 `Total` 仍是未过滤的总数，
所以搜索 + 分类同时使用时页数只是近似。没做回填（原项目的本地 catalog 没这个
问题，见下文）。

## 已验证的 GameBanana API 事实（2026-10-20 实测）

### 服务端只认两个过滤参数

| 参数 | 说明 |
| --- | --- |
| `_aFilters[Generic_Game]=20948` | 限定 Deadlock |
| `_aFilters[Generic_Category]=<id>` | 分类，**同时接受根分类 id 和子分类 id** |

`Generic_Category=33295`（Skins）→ 3331 条；`=33328`（Yamato）→ 63 条。
所以**英雄筛选可以服务端做**，不必像原项目那样在客户端过滤。

未知的过滤名一律 `UNKNOWN_FILTER` 硬拒绝。试过并确认不认的：
`Generic_SubCategory`、`Generic_Tag`、`Generic_ContentRating`、
`Generic_AdultContent`、`Generic_Nsfw`、`Generic_Visibility`、
`Generic_HasFiles`、`Generic_IncludeObsolete`。

注意这个错误**有时带 400、有时带 200**，body 一样。客户端已经能认出来
（`apiFailure`），拼错一个过滤名会拿到 API 的原话而不是一个空列表。

三类参数的行为不同，别混：

- 无效 filter → **报错**
- 无效 `_sSort` → **静默回退**到默认排序
- `_idGameRow`、`_sInitialVisibility` → **接受但静默忽略**

### 分类和英雄列表是活的

```
Mod/Categories?_idGameRow=20948&_sSort=a_to_z      → 8 个根分类
Mod/Categories?_idCategoryRow=33295&_sSort=a_to_z  → Skins 的 44 个英雄
```

`_sSort` 只认 `a_to_z` 和 `count`（默认值 `most_items` 反而不认）。
返回的每一项带 `_idRow` 和 `_nItemCount`，可以直接喂给 `Generic_Category`。

根分类 id：Animations 47611、Gameplay Modifications 33331、HUD 31713、
Maps 37225、Model Replacement 33154、Other/Misc 31710、
Quality of Life/Fixes 46154、Skins 33295。

### NSFW 没有服务端过滤，只能看记录里的字段

- `_sInitialVisibility`：`show` / `warn` / `hide`
- `_bHasContentRatings`（Index 里有）
- `_aContentRatings`（Profile 里有，是个 map；非 NSFW 时**整个字段不存在**）

4 页 200 条采样：`show` 156、`warn` 23、`hide` 21；`_bHasContentRatings=true`
46 条。第 1 页 50 条的交叉表显示两者基本等价——`warn` 和 `hide` 全部
`hasContentRatings=true`，`show` 里只有 1 条例外。

**默认列表里 `warn` 和 `hide` 都在**，不过滤就会直接看到。

GameBanana 网站自己的做法是不隐藏而是打码：页面里有
`data-_sNsfwThumbnailType="common"` 和 `<filter id="NsfwPreview">` 的
`feGaussianBlur stdDeviation="10"`。

### 分类字段在两个接口上名字不同

| 接口 | 根分类 | 子分类 |
| --- | --- | --- |
| `Mod/Index` | `_aRootCategory` | `_aSubCategory` |
| `Mod/{id}/ProfilePage` | **没有这个字段** | `_aSuperCategory` + `_aCategory` |

## 原项目怎么做的

原项目走的是完全不同的路子：后台把 GameBanana 上 Deadlock 的全部索引爬进
本地 SQLite（`catalog/`），筛选、排序、分页、搜索全在本地 SQL 里做。发给
API 的请求只带 `_aFilters[Generic_Game]`，没有任何筛选参数。

- NSFW 判据：`_sInitialVisibility ∈ {hide, warn}`，或 `_aContentRatings` 的
  key 命中 `["st","sa","sc","ft","lp","pn","nu"]`（`normalization.rs:10-12`）。
  只算性相关分级，gore 和粗口不算。
- 默认 `hideNSFW: false`（不隐藏）。三层开关：全局设置、商店 Filters 下拉里
  的 Hide NSFW / NSFW Only（两者互斥）、每项「已查看」覆盖。
- 英雄靠 category 派生，注册表是硬编码且由 `packages/shared/src/constants.ts`
  的 `DeadlockHeroes` 枚举代码生成的（`generated_hero_registry.rs`）；
  分类信息不够用时用模组名猜（`hero_registry.rs:31-57`）。

## 分叉：要不要也做本地 catalog

**已决定不做**：继续按页实时查 API，轻得多。下面的对比留作以后翻案的依据。

原项目那套换来的是：NSFW 客户端过滤没有分页洞（过滤和 `COUNT(*)` 用的是同一个
query）、facets 不随结果集变、SQLite FTS5 本地搜索、收藏、离线可用、筛选瞬时。
代价是一个同步子系统：建表、增量游标、全量快照对比打 tombstone、陈旧提示。

现在的 Go 版是按页实时查 API，轻得多：

- **走服务端筛选** —— 分类和英雄用 `Generic_Category`（比原项目的名字猜测更准），
  NSFW 仍然只能客户端过滤，会打乱每页 50 条的数量，要么接受每页变少要么回填。
- **走本地 catalog** —— 功能对齐原项目，但是一个不小的新子系统。
